1. What Continuum does

When a team member leaves, their knowledge is scattered across a repository, chat, notes and a task board. Continuum rebuilds the project's current state from those sources and produces a handover in which every statement points to its source and carries an evidence state. It asks the leaver only the questions the evidence cannot answer, a reviewer approves exactly what goes out, and the successor sees only what their role may read.

Users: reviewer (team lead or mentor), leaver, successor, plus a workspace admin planned for Round 3. Setting: small software teams (3 to 25 people), mainly student clubs where members rotate every semester.

Evidence states (shown as an icon plus text on every claim, never colour alone)

StateMeaning
VerifiedA source states it directly and an automated check confirmed the source supports it.
InferredReasonable conclusion not stated in any source; the text carries "AI inference, not stated in any source".
ConflictingSources disagree; both sides are shown; never auto-resolved and the newest is not assumed correct.
MissingSomething a handover needs has no evidence; becomes a Gap Interview question.
ConfirmedA person (reviewer or leaver) confirmed or corrected it; who and when are recorded.

The five-step workflow (as it runs today)

  1. Connect: a reviewer creates a handover (leaver, successor, successor role, date) and connects sources. Each source reports ok, partial or failed, with a reason.
  2. Reconstruct: a background job parses evidence, masks secrets and personal data, and has the AI extract atomic claims that must cite evidence.
  3. Verify: code checks every citation; a second narrow AI check decides support; conflicts and gaps are detected; a readiness score is computed with its formula visible. The leaver answers the Gap Interview and the answers become new citable evidence.
  4. Review: the reviewer approves, edits, rejects, redacts or marks claims sensitive. Publishing is blocked until conflicts are resolved (or marked "unresolved, successor to follow up") and every claim is reviewed. Publishing locks the version.
  5. Handover: the successor opens "Start here" (7 sections), clicks source chips to read the original text, and acknowledges each section or flags it unclear.

Screenshots: live site, 9 Nov 2026, automated Chrome run.

2. Architecture and data flow

1. SourcesGitHub (README, commits, PRs and comments, issues, TODO scan) · Slack-format chat export (.zip) · notes (.md, .txt, .pdf) · Exit Q&A from the leaver
→
2. Ingest and protectParse into evidence units; drop bots and one-word noise; thread chat; detect and mask secrets, emails and phone numbers; attach an access label (public / contributor / lead_only)
→
3. Evidence storePostgreSQL on Supabase; each unit keeps its label; row-level-security policies in the migration
4. Permission before generationContributor-level evidence and lead-only evidence are processed in separate passes, so lead-only text cannot leak into other claims
→
5. Extract (AI)Gemini, batches with stable evidence ids; output only through a JSON schema: type, statement, workstream, topic key, citations (evidence id plus exact quote)
→
6. VerifyCode: ids exist, quote matches the source (fuzzy, rapidfuzz). AI: "supports / partially / does not". Only "supports" can be Verified; others are dropped or labelled Inferred
7. Merge, conflicts, gapsGroup by topic; contradiction check; required topics (deploy, payments, auth, email, storage) become Gap Interview questions; readiness score
→
8. Human reviewApprove, edit, reject, redact, mark sensitive; resolve or defer conflicts; version history; publish locks the version
→
9. Role-scoped handoverA claim is shown only if the viewer's role may read all of its cited evidence; hidden items appear as a count only; acknowledge or flag unclear

Key design decisions

  • Claims, not summaries. The handover is built from atomic claims, each with a state and citations, so it can be checked line by line.
  • Trust by construction. Free text from the model is rejected; only schema-bound claims that cite real evidence ids survive, and "Verified" requires both the deterministic quote check and the support check.
  • Most restrictive label wins. A claim takes the most restrictive access label among its evidence; if the viewer cannot see all of it, the claim is hidden.
  • Small explicit pipeline. No agent framework: plain steps that can each be tested.
  • Failure handling. Every source shows ok/partial/failed with a reason; the web client retries with back-off on network errors and 502/503/504, shows a "Waking the server" banner, and shows a friendly error with Retry on every screen.
  • Frontend structure. One API facade (web/lib/api.ts) serves either a real backend or an in-browser mock seeded with the demo project; the same UI code runs both, which is how the UI was built and tested before the backend was live. The live site runs against the real API.

Known limitations (stated on purpose)

  • Free-tier speed. On 9 Nov a single approval took 6 to 10 s, which blocked reaching Publish. After a bulk endpoint and faster writes, measured on 10 Nov: single approval 1.4 to 1.9 s, bulk about 2 s (single samples). The free tier can still be slow after idle: the API took 33 s to answer its first request after a long idle, and the web shows a "Waking the server" message.
  • Role is not a verified login. The role is chosen in the UI and sent in a header, so anyone who sets the header acts as that role. Row-level-security policies exist in the database but the demo relies on the API's role checks.
  • Model variability. Gemini output differs between runs; the free tier allows about 20 requests per model per day, so the demo handover replays a stored real run and new handovers run the live pipeline.
  • Demo-data quirks. "Project in five lines" now has 5 claims (it was empty on 9 Nov). The same Render-vs-Vercel disagreement still appears as two conflict cards, although resolving one settles both. Some dates may show the ingest date (not re-checked).
  • Scope. Built for small software teams and the demo project; not tested at scale, on other repositories, or with a screen reader. A real-phone run was done on 10 Nov for create, reconstruct, view, export, the Successor view and acknowledging a section; publishing on a phone and the 15-minute cold start have not been done yet.

7. Three improvements committed for Round 3

  1. Cross-source conflict resolution. Round 2 detects conflicts per topic and lets a reviewer resolve or defer each one. Round 3: project-wide contradiction detection across sources and time, merging duplicates of the same disagreement, a side-by-side resolution screen with the evidence on both sides, and a resolution history.
  2. Acknowledgement loop with version diff. Round 2 records acknowledge/unclear per section. Round 3: "unclear" flags routed back to the reviewer and leaver as tasks, and a working version diff (claims added, edited, rejected, with before and after text). Already started: the diff screen and the backend diff endpoint both work (10 Nov); routing unclear flags back as tasks is still to do.
  3. Sensitive-data protection. Round 2 masks secrets and PII and hides lead-only claims. Round 3: a redaction review queue, a Guest role, a full audit log that also covers views and exports, and export of the approved handover with citations as links. Already started: the audit page and the Markdown/print export exist; views and exports are not yet logged.
